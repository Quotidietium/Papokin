# 性能优化轮次 4：区块编码缓存逐出策略（字节预算 + 最远优先）

> 日期：2026-10-04 ｜ 版本：0.3.16+1.21.11 ｜ 类别：内存
> 量化数据：`round4-chunk-cache-prune.json`（同目录）｜ 基准：`benchmark/src/bin/chunk_cache_prune.rs`

## 问题陈述

每玩家的 `chunk_encode_cache`（`player.rs`，跨 tick 复用区块序列化结果）旧策略为**计数闸 + 整体清空**：

```rust
const MAX_ENCODE_CACHE_ENTRIES: usize = 8192;
if cache.len() > MAX_ENCODE_CACHE_ENTRIES { cache.clear(); }
```

两个结构性缺陷：

1. **计数不代表字节**。8192 条 × 典型编码负载（区块包 + 光照包 ≈ 20 KiB）理论上限 ≈ 160 MiB/玩家——且只有超限那一刻才干预，此前无界增长。轮次 3 已把单条目容量浪费归零，但条目数本身仍无字节约束。
2. **清空风暴误伤热数据**。玩家旅途移动时缓存随探索持续积累，触闸瞬间**全部作废**——包括当前视距内即将重发的热区块。清空后第一批重发全部重新序列化，形成周期性的 CPU 尖峰（每轮清空 ≈ 8300 次额外编码），随后缓存重新爬升，周而复始。

## 修复方案

改为**字节预算 + 最远优先逐出**（`player.rs:2579` 起、`chunk_sender.rs:395` `prune_encode_cache`）：

- 预算 `MAX_ENCODE_CACHE_BYTES = 32 MiB`：每 tick 求和 `EncodedChunk::encoded_bytes()`（区块负载 + 光照负载），超预算才逐出；
- 逐出目标 = 预算的 80%（`MAX / 5 * 4`）：留足余量，避免每 tick 贴着预算反复逐出；
- 逐出顺序 = 距玩家当前区块**最远优先**：旅途移动中远处区块几乎不再重发（视距单向推进），跨世界条目天然最远。排序键为切比雪夫近似的平方距离（`dx²+dz²`，i64 无溢出）。

为什么是最远优先而不是 LRU：该缓存的访问模式由玩家位置驱动，「最近用过」与「即将再用」相关性弱于「距离近」；且 LRU 需要每条目维护时间戳/链表，最远优先只在逐出时一次排序（触发频率实测每 9600 tick 715 次，均摊可忽略）。

## 基准方法

`chunk_cache_prune`：旅途模拟——玩家以视距 12（与生产 `Cylindrical` 视锥同一公式）沿确定性随机路径行进 9600 tick，每 tick 至多移动 40 次微步；区块尺寸坐标确定性生成（3-200 KiB 剖面同轮次 3）。两模式跑同一旅程：

- **old**：>8192 条即整体清空（0.3.16 前行为复刻）；
- **new**：>32 MiB 即最远优先逐出至 80%（本提交行为复刻）。

记录缓存峰值字节/条目、全程编码次数（CPU 代理指标）、单 tick 编码峰值；两模式**发送流哈希**（每 tick 发出的区块键序列）必须全等，作为功能一致性硬闸门。

## 结果

| 策略 | 缓存峰值 | 条目峰值 | 总编码次数 | 单 tick 编码峰值 | 策略触发 |
|---|---:|---:|---:|---:|---:|
| old（计数闸清空） | 170.6 MiB | 8185 | 257 920 | 585 | 31 |
| new（字节预算逐出） | **32.0 MiB** | 1745 | **240 560** | 585 | 715 |

- **缓存峰值 170.6 → 32.0 MiB（-81.2%）**，且新策略的峰值即预算本身——内存占用从「随旅程无界爬升至闸值」变为「恒定有界」。
- **总编码次数 -6.7%（257 920 → 240 560）**：清空风暴把视距内热条目一并作废，31 次清空 × 每次 ≈560 块重编码 ≈ 17 360 次白干；最远优先只逐出冷数据，热条目全程存活。
- 单 tick 编码峰值不变（585）：两种策略都不改变「新世界区块必须现编」的下界。
- 完整性闸门：两模式发送流哈希全等（`integrity_ok: true`）。

## 红线核对

- **安全性**：无 unsafe；逐出只删缓存条目，弱引用新鲜度校验（条目随区块数据变化失效）语义不变；`prune_encode_cache` 对 `BuildHasher` 泛化，不绑定具体散列实现。
- **稳定性**：`cargo test -p papokin --lib` 全绿（含新增 `prune_encode_cache_evicts_farthest_first_within_budget`：近留远逐、幂等、内容不变）；clippy `--all-targets -D warnings` 零告警。
- **兼容性**：线上字节零改动——缓存只影响「是否重编」，不影响「编码出什么」；基准发送流哈希全等双闸门。
- **用户体验**：重发行为逐字节一致；逐出不再制造周期性 CPU 尖峰（31 次清空风暴 → 715 次微量逐出，单次成本从 ≈8300 编码降至 ≈25 编码）。
