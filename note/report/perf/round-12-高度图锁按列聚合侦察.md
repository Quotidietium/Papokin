# 轮次 12：高度图互斥锁「按列聚合」量化侦察（结论性轮次，零生产改动）

> 日期：2026-10-04 ｜ 主题：CPU（`ChunkData::heightmap` 互斥锁竞争收编可行性）
> 基线：轮次 11 收官（0.3.23）；**本轮无生产改动**（收益场景在生产不可达，按「不堆无收益改动」原则止步于量化）
> 基准程序：[benchmark/src/bin/heightmap_lock_batch.rs](../../../benchmark/src/bin/heightmap_lock_batch.rs) ｜ 原始数据：[round12-heightmap-lock-batch.json](round12-heightmap-lock-batch.json)

## 1. 侦察动机

轮次 11 负结果后转向 CPU 面。普查发现 `ChunkData.heightmap: Mutex<ChunkHeightmaps>`
的访问模式存在「逐方块锁」与「按列聚合锁」两种形态：

- `set_block_absolute_y`（生产运行时主路径）：每次调用经 `update_heightmap`
  独立 `lock()` 一次，**锁次数 = 方块数**；
- `set_blocks_batch`（仅 `fill` 命令使用）：整批一次锁 + `changed_columns`
  聚合，**锁次数 = 1**。

高度图更新本身只依赖**该列最终状态**（同列后写覆盖先写），逐方块锁在
批量场景下理论可聚合。列为收编候选。

## 2. 量化结果（基准实测）

模型：单区块 16×16 列 × 每列 256 方块（自底向上铺满，对应一次
16×256×16 填充/大批量编辑，与 `fill` 上限同量级）。

| 路径 | 锁获取次数 | 耗时 |
|---|---|---|
| 逐方块锁（生产 `set_block_absolute_y` 现状） | 65,537 次 | 2.5 ms |
| 按列聚合锁（`set_blocks_batch` 形态） | **2 次** | 0.0 ms |

**锁次数 -100%（65,537→2）、耗时 -99.9%**，高度图内容 FNV-1a 逐字节全等。

## 3. 关键约束：收益场景在生产不可达

基准量化的收益**真实且巨大**，但落库前必须核对生产调用面：

- **生成期**（populate、carver、结构放置——真正的批量方块来源）全部走
  `ProtoChunk::set_block_state`，该类型**不持有 `ChunkData`、无互斥锁**，
  高度图经 `maybe_update_surface_height_map` 等无锁路径维护。
  **批量场景天然无锁可省。**
- **运行时 `ChunkData` 路径**的唯一生产主入口是 `World::set_block_state`
  （单方块 API：方块放置/破坏、活塞、流体扩散、植物生长），每次调用
  **语义上只设一块**，逐方块锁是单方块语义的固有问题，无批量可聚合。
- 唯一批量运行时入口 `set_blocks_batch` 已是最优形态（单锁 + 列聚合），
  且已被 `fill` 命令使用。

**结论：基准证实的「批量锁竞争」热点在生产中不存在——批量场景走无锁
`ProtoChunk`，有锁场景是单方块 API 的固有语义。** 没有可收编的对象。

## 4. 处置：零生产改动

按「不为不可达收益堆代码」与「行为不一致是红线」原则，本轮不落地任何
生产改动，仅保留基准程序与本报告。`papokin-world` 270 测试、clippy 全绿，
与轮次 11 基线逐字节一致。

## 5. 方法论沉淀

性能战役第二个**结论性轮次**，与轮次 11 共同确立一条纪律：

> **基准量化的收益 ≠ 可落地的收益。** 基准能证明「若存在批量锁则省」，
> 但不能证明「生产存在该批量锁」。落库前必须回答两个问题：
> ① 收益场景在生产中真实发生吗？② 它走的是被优化的那条代码路径吗？
> 本轮 ②不成立——批量走无锁 `ProtoChunk`，有锁的是单方块 API。

连同轮次 11（教科书式分配反模式需实测），两轮共同把后续侦察的门槛
从「找到理论热点」提高到「找到**生产可达**的理论热点」。

## 6. 硬闸门

| 闸门 | 结果 |
|---|---|
| 高度图内容字节全等（FNV-1a） | ✅ 通过 |
| 聚合路径锁次数 < 逐方块路径 | ✅ 通过（65,537→2） |
| **收益场景生产可达** | ❌ **不成立（批量走无锁 ProtoChunk）** |

第三个闸门是本轮判决条件：收益不可达，故不落地。

## 7. 后续方向（轮次 13 候选）

- 运行时单方块路径的**锁内操作**优化：`update_heightmap` 的列扫描
  （`populate_heightmaps`）在单方块 set 时是否做了整列重扫——若有，
  单方块场景可收窄为增量更新，收益生产可达；
- `Level::read_chunk_sync` 的 DashMap 分片锁在高频 `set_block_state`
  （流体/红石 tick）下的竞争；
- 世界 tick 的 `chunks_with_scheduled_ticks` 逐 tick 全量 `collect`
  （`level.rs:644` 注释已标死锁规避，但每 tick 一次全 Vec 收集是分配流失）。
