# 轮次 9：压缩资源（zlib 上下文 + 压缩暂存）全局有界池

日期：2026-10-04　类型：内存优化（轮次 8 的生产拓扑修正 + 轮次 2 潜在缺陷修复）　状态：已落库并过门禁

## 背景：轮次 8 模型的生产拓扑修正

轮次 8 把每连接常驻的 zlib 压缩上下文（实测 313 KiB/份）改为**线程局部**池，
单线程基准测得 128 连接负载 39.2 MiB → 337 KiB（-99.2%）。但复核生产调用
拓扑发现该模型不成立：压缩实际发生在 `frame_batch_maybe_offload`
（`net/java/mod.rs:222`）投出的 `tokio::task::spawn_blocking` 上——任何包含
可压缩包的批次都整体移交 tokio **阻塞线程池**执行。阻塞池按需扩张（上限
512 线程），tick 齐发的批量压缩会让大量阻塞线程各沾一次压缩；线程局部池
下驻留量 ≈ 沾过压缩的线程数 × 单份大小，**满负载（线程数≈连接数）时池化
收益归零**。本轮基准以多线程工作分区模型证实：

- W=16（常态并发）：线程局部池驻留 8.79 MiB（有效，-87.1%）；
- W=128（tick 齐发极端）：线程局部池驻留 **68.2 MiB ≈ 旧行为**（收益归零）。

结论：池拓扑必须对线程数免疫。同时发现压缩暂存（每连接 ≤ 256 KiB，轮次 2
治理）与压缩上下文在 `frame_packet` 压缩分支中成对使用，适合捆绑入同一池。

## 顺带修复：轮次 2 引入的暂存预留不足潜在缺陷

审查 `compress_packet_data` 的预留惯用法时发现：历史上按
`scratch.reserve(reserve_hint - current_capacity)` 传参，而 `Vec::reserve`
的 additional 语义只保证容量 ≥ len + additional（此处 len 为 0），摊销扩容
取 `max(2×容量, hint-容量)`——当既有容量 < hint/2 时结果仍小于 hint。
`flate2::Compress::compress_vec` 只写既有备用容量（源码核实
`write_to_spare_capacity_of_vec`，无内部扩容），不可压缩大包因此写满备用
容量得到 `Status::Ok`，触发「Unexpected compressor status」组帧失败并断开
连接。触发窗口：暂存容量经收缩治理回落后（≤ 256 KiB），再来约 ≥ 480 KiB
的不可压缩包（hint/2 反超既有容量）。轮次 2 的每连接 scratch 与本轮池化
暂存共用同一惯用法，均受影响。修复：clear 后**全量** `reserve(hint)`（容量
足够时 reserve 内部自然短路，零成本），并加回归测试
`progressive_growth_never_under_reserves_scratch`（300 KiB → 700 KiB 不可
压缩包序列，精确落入缺陷窗口）。

## 实现

`crates/papokin-protocol/src/java/packet_encoder.rs`：

- 删除轮次 8 的线程局部 `COMPRESSOR_POOL` 与编码器的 `compression_scratch`
  字段（`frame_scratch` 因跨 await 使用保留每连接，不在本轮）；
- 新增全局（跨线程）池 `COMPRESSION_RESOURCE_POOL: Mutex<Vec<CompressionResources>>`：
  条目捆绑一份压缩上下文 + 一块压缩暂存；驻留上限 16 份（**只约束驻留、
  不约束并发**——池空时检出永远新建，压缩路径绝不因池化阻塞）；
- 守卫 `PooledCompressionResources` 以**来源池引用**为参数（生产传全局静态，
  测试传栈上局部池）——池状态断言与并发测试天然隔离，无需串行锁；
- 归还治理：暂存容量逾 `2 × MAX_RETAINED_SCRATCH` 收缩回 256 KiB（近似
  轮次 2 半量规则，防振荡）；
- `compress_packet_data` 改自由函数（返回持有压缩结果的守卫），预留改
  全量（上述缺陷修复）；`frame_packet` 压缩分支改早返回自收尾，两条
  未压缩路径共享同一收尾（顺带消除 `payload_to_write` 绑定）；
- 诊断 API `scratch_capacity() -> (usize, usize)` 收缩为
  `frame_scratch_capacity() -> usize`（无外部调用方）。

## 测试

- 池行为（局部池注入，无锁隔离）：复用往返（1→0→1）、上限钳制（17 份
  守卫归还钳在 16）、归还治理（1 MiB 撑大后归还收缩 ≤ 256 KiB；128 KiB
  常规尺寸不触发振荡）；
- 回归：渐进增大不可压缩包预留不足（见上节）；
- 字节全等门：跨编码器实例压缩输出逐字节一致（轮次 8 测试沿用）；
- 轮次 2 的两个 scratch 治理测试重写为：组帧 scratch 收缩/防振荡 +
  线上帧结构断言（异步、不触碰池状态），与未压缩帧 `data_length=0`
  标记断言；protocol lib 140 项全绿，world 270 + 主仓 407 与工作区
  clippy 全绿。

## 基准（`benchmark/src/bin/compression_resource_pool.rs`）

128 连接 × 300 包/连接 = 38,400 包，按 `conn % workers` 静态分区到
W 个工作线程（等价池化拓扑下的稳态派发），两种拓扑 W=16 / W=128；
真实 flate2 压缩 + 计数分配器测驻留。三策略对比：

| 拓扑 | 策略 | 驻留字节 | 资源创建 | 全程耗时 |
| --- | --- | ---: | ---: | ---: |
| W=16 | legacy（每连接常驻） | 68,205,693（65.0 MiB） | 128 | 520.1 ms |
| W=16 | 线程局部池（轮次 8） | 8,786,704（8.38 MiB，**-87.1%**） | 16 | 500.5 ms |
| W=16 | 全局有界池（轮次 9） | 8,698,968（8.30 MiB，**-87.2%**） | 16 | 561.8 ms |
| W=128 | legacy | 68,208,381（65.0 MiB） | 128 | 370.6 ms |
| W=128 | 线程局部池（轮次 8） | 68,226,813（65.1 MiB，**+0.03% 归零**） | 128 | 398.0 ms |
| W=128 | 全局有界池（轮次 9） | 8,404,852（8.02 MiB，**-87.7%**） | 32 | 470.4 ms |

硬闸门：两种拓扑下三策略逐包输出哈希全等、线上字节总数相等。

要点解读：

- 单连接资源捆绑 ≈ 533 KiB（313 KiB 上下文 + 平均约 220 KiB 暂存）；
  全局池把驻留封顶为 16 份 ≈ 8.3 MiB，**与线程数、连接数均无关**——
  W=128 极端下仍守住 -87.7%，线程局部池在同一极端下退化为旧行为；
- 代价：全竞争（W=128）下全局池墙钟 +18%（470.4 vs 398.0 ms），源于
  每包两次短锁（检出/归还）与 16 份之外的创建-释放抖动（32 份创建）。
  生产中压缩耗时以区块编码为主体（互斥开销占比远低于本基准的纯压缩
  回环），且该开销换来的是驻留的有界性——属有意取舍，如实记录；
- W=128 下线程局部墙钟 398.0 ms 优于 legacy 370.6 ms 的表象系测量噪声
  （两者资源形态相同，差异来自调度），不作为结论。

## 对轮次 8 的勘误

轮次 8 报告中的「-99.2%」为单线程模型结果；生产 `spawn_blocking` 拓扑
下线程局部池在满负载时收益归零（本轮 W=128 场景实测）。轮次 8 的方向
（池化 + 逐包无状态语义）不变，池拓扑由本轮修正为全局有界。
