# 轮次 41：NBT 复合标签键内联侦察（结论性轮次，零生产改动）

> 日期：2026-10-12 ｜ 主题：内存（轮次 40 终态的逐键堆分配消除可行性）
> 基线：轮次 40 收官（0.3.51）；**本轮无生产改动**（驻留闸门未过，按战役纪律回退归档）
> 基准程序：[benchmark/src/bin/nbt_key_inline.rs](../../../benchmark/src/bin/nbt_key_inline.rs) ｜ 原始数据：[round41-nbt-key-inline.json](round41-nbt-key-inline.json)

## 1. 侦察动机

轮次 40 把复合标签容器换成 `NbtMap`（插入序 Vec 承载）后，键仍是逐键
`Box<str>` 独立堆分配：请求字节口径下恰为 len 字节，Win32 堆 16B 粒度
下实占至少 16B 外加块管理开销。而 NBT 键绝大多数很短（`Pos`/`Air`/
`Motion`/`Health`…），基准语料抽样 1323 键中 1228 键（**92.8%**）
≤22 字节——初判是「内联进枚举消灭逐键分配」的标准场景：

```rust
enum KeyInline {
    Inline { len: u8, buf: [u8; 22] },  // 短键零堆分配
    Heap(Box<str>),                     // 超长键回退
}
```

条目从 `(Box<str>, NbtTag)` 48B 变 `(KeyInline, NbtTag)` 56B
（键 16B→24B，值 32B 不变）。

## 2. 关键发现（负结果的算术）

双臂基准（与轮次 40 同负载：15000 复合标签三形语料，旧臂在基准内
复刻轮次 40 终态，新臂装载内联键形态；语义等价经「序列化字节 →
生产解析器回读 → canonical 键序无关指纹」中立法官证明）。预登记
闸门四条，实测：

| 闸门 | 结果 |
|---|---|
| 构建内容 canonical 指纹全等（生产解析器回读） | ✅ `0x6a2c51aeca019863` 全等 |
| 查找电池命中与值指纹全等 | ✅ `0x3f8632d588b5d2c8`，命中 1666=1666 |
| **驻留字节下降（本轮主判据）** | ❌ 35 615 310 → 37 916 289 B（×0.939，**+6.4%**） |
| 构建分配次数下降 | ✅ 775 337 → 403 294（−372 043，−48%） |

净驻留反升的算术分解：

- **成本项**：条目 +8B **无差别**作用于全部约 40 万条目（含 7.2%
  超长键条目——它们付了 +8B 却不享受内联），且 entries Vec 增长链
  的容量余量按每槽 +8B 同步放大，合计约 +3 MB 级；
- **节省项**：仅 92.8% 键的字符串本体字节。请求字节口径下
  `Box<str>` 分配恰为 len 字节（无头部/对齐放大），而 NBT 短键
  均值远低于 8B/键的收支平衡线——`Pos`(3B)/`Air`(3B) 内联后省
  3B、条目却多付 8B，净亏；合计节省仅 ~1.5 MB 级；
- 两项相抵：**+2.30 MB（+6.4%）**。

本质：上一轮 `HashMap`→`NbtMap` 能赢 1.70×，是因为哈希表的
**结构性开销**（表槽余量/控制字节/rehash 链）远大于字符串本体；
这一轮的对手只剩字符串本体本身，比条目膨胀的 +8B 还小。

副产物（CPU 全线小胜但不足以翻案）：构建 1.21×（39.82→32.91 ms）、
查找 1.10×、序列化回读 1.19×、深克隆 1.69×，分配次数全线下降
（构建 −48%、克隆 −62%、序列化 −22%）。按 Win32 真实堆口径建模
（16B 粒度 + 块开销），被消除的 37 万笔小分配折算后净收益约
−3%——方向转正但幅度仍远低于战役收编门槛，且请求字节口径
（与进程驻留更贴近的主判据，预登记写死）明确为 +6.4%。

## 3. 结构性上限：16B 键枚举不可达

本设计的理论最优是「条目不涨」的 16B 键枚举，Rust 布局规则下
不可达成：

- 枚举尺寸 = 最大变体载荷 + 判别标签，按变体对齐取整；
- `Heap(Box<str>)` 变体载荷即 16B（胖指针，8 对齐），任何判别标签
  都把尺寸推到 24B；
- `Box<str>` 无可用 niche（指针只要非空即任意值、len 任意），
  自动布局无法把判别位藏进指针槽；
- 手工 niche 打包（union + 判别位占指针槽空值）需 unsafe，且内联
  容量只剩 ~13B——`fall_distance`(13)/`Invulnerable`(12) 一线键
  全部落堆，覆盖率骤降，复杂度与覆盖率双输；
- 若直接把内联阈值压到 ≤13B，92.8% 覆盖率显著缩水，节省进一步
  萎缩，等式更差。

结论：`NbtTag` 32B + 键 16B + 条目 48B（轮次 40 终态）已是该容器
在 Rust 自动布局下的近优解。

## 4. 同场评估并否决的替代设计

- **字符串驻留（intern 表）**：触碰 DoS 红线——网络侧 `custom_data`
  的键空间无界，驻留表等于无界泄漏；
- **有界静态键池**（预登记常见键）：覆盖不全是本性（插件/数据包
  可造任意键），池外回退路径使双形态代码长期共存，脆弱；
- **`NbtTag` 变体装箱**（压 32B→16B）：解析路径每标签多一次分配，
  轮次 24 已证解析态分配是驻留主源，方向相反。

## 6. 方法论沉淀

1. **内联赢的是分配器粒度，输的是容器槽宽**——每条目无差别成本
   对逐键概率性节省，必须先做收支算术再动手；
2. 请求字节口径与真实堆口径结论可以相反（+6.4% vs ~−3%），
   主判据口径必须在预登记闸门里写死（本战役取请求字节）；
3. 该容器的键/值形态优化已到布局下限，后续内存探查应转向
   **驻留生命周期**（谁在长期持有复合标签、何时可释放/落盘），
   而非继续压形态。
