# 轮次 22：世界三表峰值桶驻留回收（实体/计划刻/方块实体）

> 日期：2026-10-04 ｜ 主题：内存（驻留容量） ｜ 闸门：5/5 PASS
> 基准：[benchmark/src/bin/world_tables_bucket_reclaim.rs](../../../benchmark/src/bin/world_tables_bucket_reclaim.rs)
> 数据：[round22-world-tables-bucket-reclaim.json](round22-world-tables-bucket-reclaim.json)

## 问题

继轮次 21（编码缓存桶回收）后对全仓长生命周期可增长表做系统清点，
「移除条目但桶数组永不收缩」的同族问题还有三张世界级表：

| 表 | 位置 | 峰值驱动 | 现状移除路径 | 桶驻留 |
| --- | --- | --- | --- | --- |
| `entity_map` | `entity_tracker.rs:529` | 刷怪塔/袭击事件（万级实体） | 消失时 `remove` | 峰值槽位永久驻留 |
| `chunks_with_scheduled_ticks` | `level.rs:93` | 流体/岩浆扩散（万级区块） | 消化后 `remove`（`level.rs:678`） | 同上 |
| `block_entities` | `world/mod.rs:308` | 大型机器区加载 | 区块卸载 `remove`（`world/mod.rs:4650`） | 同上 |

生产量级估算：5 万实体事件后实体表桶数组约 1.2 MB（3.7 万槽 ×
32 B）驻留至服务器重启；2 万计划刻 + 3 万方块实体区块各约
0.2-2.3 MB。三张表均为每世界一张，多世界（主界/下界/末地）叠加。

侦察插曲：dashmap 的 `remove` 会顺带收缩个别低占用分片（实测
8192 条目表移除一半后总容量 12936→12330，约 5%）——只摊平
分片内墓碑，远不能回收整表峰值，三处机制仍然必要。

## 清点中已排除的项（如实记录，防重复探查）

- `save_locks`（`player_data.rs:23`）：已有 `prune_save_lock` 在全部
  三条路径回收（`remove_if` 强计数为 1 谓词 + 分裂窗口论证），
  仅桶数组残留而峰值 = 并发在途保存数，量级可忽略；
- `seen_by`（`entity_tracker.rs:38`）：4× 滞回 + 地板 64 的规则下，
  现实观察者数（<64）全部落在滞回带内，机制会天然失效；且
  移除收尾时整个 `TrackedEntity` 随 `entity_map` 条目释放，
  桶不跨实体驻留。不立项；
- `entity_index` 桶（`entity_index.rs`）：查询路径已惰性剔除死
  弱引用并对空桶 `remove_if`，残留仅限「实体曾到访且其后从不
  被查询」的远端区块，数十字节级，量级不立项；
- `loaded_chunks` / `loaded_entity_chunks` / `chunk_watchers`：
  `clean_memory` 已有 4096 槽位余量收缩（既有先例）；
- 静态注册表（轮次 21 已记录否定结论）。

## 机制

1. **`entity_map` 滞回收缩**（`entity_tracker.rs::update_all` 尾部，
   新增私有辅助 `maybe_shrink_buckets`）：
   `map.capacity() > map.len() × 4 + 64` 时 `shrink_to_fit()`——
   与轮次 21 编码缓存同参数。插入点安全性：
   - `update_all` 由世界 tick 单线程调用，且被
     `update_all_scratch` 互斥锁序列化，无并发 shrink 重叠；
   - 插入点不持有任何 `entity_map` 分片守卫（快照 `extend`
     早已结束，`tracked_entities` 持的是 Arc 克隆）；
   - dashmap 6 `shrink_to_fit` 逐分片顺序写锁，并发
     `insert`/`remove`（生成/消失路径）仅短暂 park；
   - 4× 滞回使实体数回涨 4 倍内不再收缩，防振荡。
2. **`chunks_with_scheduled_ticks` 余量收缩**（`level.rs::clean_memory`
   内，与既有三表并排）：沿用同函数既有的
   `capacity() - len() >= 4096` 规则，100 tick 周期天然限频。
3. **`block_entities` 余量收缩**（`world/mod.rs::tick_environment`
   的 100 tick 块内、`level.clean_memory()` 调用点旁）：同一
   4096 规则。两处 `clean_memory` 调用点（周期 + 玩家退出）都
   幂等安全。

## 负载模型

对齐「事件高峰 → 回落 → 小幅再波动」节奏：
1. 高峰填充：实体 5 万、计划刻 2 万区块、方块实体 3 万区块；
2. 高峰回落：实体消失 90%、计划刻消化 95%（留长尾刻，贴近
   生产且避免空集指纹空采样）、方块实体卸载 90%；
3. 小幅再波动：三表各回涨约 10%（滞回/余量必须压住振荡）。

两臂：无收缩（现状 remove-only）vs 收缩（滞回 + 余量双规则）。

## 结果

| 指标（回落后） | 无收缩 | 收缩 | 差值 |
| --- | ---: | ---: | ---: |
| 实体表桶驻留 | 1,182,752 B | 229,376 B | **5.2× 回收** |
| 计划刻集桶驻留 | 208,280 B | 14,336 B | 14.5× 回收 |
| 方块实体表桶驻留 | 2,275,560 B | 143,360 B | 15.9× 回收 |
| 三表合计 | 3.67 MB | 0.39 MB | 9.5× |
| 收尾合计（再波动后） | 3.72 MB | 0.77 MB | 4.8× |
| 全程分配次数 | 26 | 32 | +6 |
| 收缩事件 | 0 | 3（每表一次） | 再波动 0 次 |

- 回落瞬间：三表桶驻留合计从 3.67 MB 回落到 0.39 MB；
- 再波动期：桶数组随回涨自然增长到当前负载适配值（0.77 MB vs
  无收缩臂的 3.72 MB 历史峰值），且**零**新增收缩——滞回与
  余量规则均压住振荡；
- 代价：全程仅多 6 次分配（3 次 shrink 重哈希 + 回涨步进差）；
- 存活指纹三表双臂全等（实体 `0x1f49…e8a2`、计划刻
  `0x4819…d85e`、方块实体 `0xe6bf…4688`，收尾采样同样一致）。

## 闸门

| 闸门 | 结果 | 说明 |
| --- | --- | --- |
| 三表存活指纹全等（双采样） | PASS | 收缩不改变存活条目集合 |
| 实体表桶驻留 ≥4× 回收 | PASS | 实测 5.2× |
| 计划刻+方块实体 ≥4× 回收 | PASS | 实测 15.8× |
| 收缩事件 ≤3 且再波动零收缩 | PASS | 实测 3 次 / 0 次 |
| 额外分配 ≤32 | PASS | 实测 +6 |

生产侧另有 2 项新单测（`entity_tracker::tests`）：全量移除后
容量 ≥4× 回收、3/4 占用滞回线内不得收缩（含 dashmap remove
顺带收缩分片的实测前提断言）。

## 结论与后续

收编：三表峰值桶驻留以 6 次额外分配换来回落后 9.5× 的驻留回落，
语义零变化（指纹全等、world 270 / papokin 409+2 全绿）。全仓长
生命周期可增长表至此完成系统清点：四张有管理（编码缓存/实体表/
计划刻/方块实体）+ `clean_memory` 既有三张 + 否定结论若干
（见「已排除的项」），峰值桶驻留族问题基本肃清。

后续候选（记入轮次 23+ 清单）：
- 线程局部分片暂存（thread_local box scratch）的跨线程峰值审计；
- 真实服务器负载下的驻留采样（sysinfo 已在 benchmark 依赖内，
  可为后续轮次提供生产量级校准）；
- NBT 序列化/网络出站 `Bytes` 链的频次加权侦察（轮次 19 遗留）。
