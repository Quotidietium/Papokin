# 09 — 存档系统重写实现记录（Papo 兼容 / 零数据风险）

> 目标：把 Papo（Paper 0.80.0 / MC 1.21.11）的存档语义用 Rust 重写进本项目，
> 使现有 Papo 存档可直接读取，且保存过程不允许任何数据风险。
> 前置分析见 [07-存档系统对比](07-存档系统对比-Pumpkin-vs-Papo.md) 与
> [08-存档格式深挖](08-存档格式深挖-Pumpkin-vs-Papo.md)。

## 版本切换：26.3 → 1.21.11

- `CURRENT_MC_VERSION` = `V_1_21_11`（协议 774），只改"最新版本回退默认值"，**不动版本门控**
  （`if *version < V_26_3` 等历史分支保留，1.21.11 客户端走正确路径）。
- 涉及 14 处：packet.rs（CURRENT_MC_VERSION + to_id 回退）、codegen LATEST_VERSION、
  text/legacy、item_stack_seralizer、ser/mod、award_stats、player.rs DATA_VERSION。
- DataVersion 统一 4671（anvil WORLD_DATA_VERSION、POI、player）。
- Cargo 版本号 `0.1.0+1.21.11-26.51`。
- 固定字节的既有测试（living/villager/synched_entity_data 等 V_26_3 上下文）保留——
  26.3 仍是受支持的历史版本。

## RegionFile 兼容层（chunk/format/anvil.rs 重写）

读取端（Papo 存档直接可读）：
- **Spigot 255 扇区扩展**：count==255 时从块偏移处读 u32 长度重算真实扇区数。
- **vanilla 外部块**：压缩字节高位 `0x80` → 载荷在 `c.<x>.<z>.mcc`，
  由新 trait 方法 `read_at(bytes, path)` 按路径加载（file_manager 已接入，
  其余格式走默认委托 `read`）。缺 `.mcc` → 该块报 per-chunk 错误，不拖垮整个 region。
- **Paper oversized（feature 0004）**：读 `r.X.Z.oversized.nbt` 位图 +
  `r.X.Z_oversized_<x>_<z>.nbt`（zlib 命名根 NBT），把 `Entities/block_entities/TileEntities`
  合并回基础块 NBT。
- **头自愈（feature 0019 语义）**：越界/解析失败的表项 warn + 跳过；<8KiB 的撕裂头文件
  视为空 region，整文件永不硬失败。
- 全部压缩格式：GZip(1)/ZLib(2)/None(3)/LZ4(4)/Custom(127)。

写入端（零数据风险）：
- **默认原子写**：tmp 文件 → `flush` → `sync_all` → `rename`。崩溃窗口内旧文件永远完整。
- **`write_in_place` 模式**：仅同尺寸覆写与 EOF 追加；尺寸变化**不再 leapfrog 搬移**，
  直接升级为原子全量重写（消除搬移窗口的邻居块损毁风险）。
- **>255 扇区 → vanilla 外部块机制**：region 表项只占 1 扇区（5 字节头 + padding），
  载荷原子写入 `.mcc`。单字节扇区计数字段**结构性不可能溢出**（修复了旧代码
  `(offset<<8)|count` 静默截断的损坏点）。
- **全量重写后偏移重编号**（`renumber_sectors`）：升级 All 时同步重排内存偏移表，
  修复旧代码"write_all 后偏移失效 → 后续就地写错位 → 覆盖头部表"的损毁隐患
  （debug_assert 校验一致性）。
- **写失败保留动作**：`write()` 出错时 `write_action` 不清零，下一轮自动重试。
- `.mcc` 清理：块回到内联后删除残留外部文件；写成功后清理 Paper oversized 边车，
  防止旧 oversized 数据遮蔽新数据。

## 区块 NBT 全字段保留（format/mod.rs + chunk/mod.rs）

- `ChunkData` 新增 `preserved_data: Mutex<Option<PreservedChunkData>>`。
- 读入时：根复合标签中**非 Pumpkin 管理键**全部原样保留——`structures`、`blending_data`、
  `LastUpdate`、完整 `Heightmaps`（含 OCEAN_FLOOR 等未建模项）、Paper PDC 等。
- 写出时：以保留字段为底重建根，管理键覆盖写入；Heightmaps 与保留项合并。
- **PDC 标签名往返**：读到 `BukkitValues` 就写回 `BukkitValues`（Papo 的 PDC 不丢名）。
- **Status 原串保留**：`minecraft:noise/surface/carvers` 等旧名在状态枚举未推进时
  原样写回，状态推进后才写规范名。
- 测试 `foreign_chunk_fields_survive_round_trip` 验证一次及两次往返。

## 其余存档面

- **玩家数据**（player_data.rs）：`.dat_new` tmp 写 → fsync → 旧文件转 `.dat_old` 备份 →
  原子换入；rename 失败退化为 copy（不再直接 `File::create` 覆盖旧档）。
- **level.dat**（world_info/anvil.rs）：`level.dat_new` → fsync → rename，rename 失败
  不再被 `let _ =` 吞掉；旧档备份 `level.dat_old` 保留。
- **POI**（poi/mod.rs）：整文件在内存组装 → tmp → fsync → 原子换入（旧代码直接
  truncate 写）。读取端本就跳过坏表项。
- **实体区块**：走 `AnvilChunkFile<ChunkEntityData>`，自动获得新原子写路径；
  格式 `{DataVersion, Position IntArray, Entities List}` 与 vanilla 一致。

## 保存管线防丢（file_manager.rs + level.rs）

- `update_chunk` 失败时**恢复脏标记**（旧代码先清脏后序列化，失败即静默丢改动）。
- `ChunkSerializer::has_pending_writes()`（新 trait 方法）：`can_remove` 在引用计数
  检查之外，还要求无未落盘数据且锁空闲——**有未写数据的 serializer 永不被逐出**，
  与失败重试配合闭环。
- 关闭时线程 join 超时 3s → 60s，避免大世界刷盘被提前放弃。
- 默认压缩 **LZ4-6 → ZLib-6**（与 vanilla/Papo 默认一致；读取端仍全格式兼容）。

## Release 构建阶段修的两个问题（2026-09-19）

1. **`debug_assert_eq!` 的 release 名字解析**：断言参数带
   `#[cfg(debug_assertions)]` 绑定在 release 下不编译但宏仍解析名字 → E0425。
   改为整个校验语句（内联表达式）一起 cfg 掉。教训：debug 测试不覆盖此路径。
   （注：先改成块形式后，clippy 的 `semicolon_outside_block` ×
   `semicolon_if_nothing_returned` 互相矛盾，最终改为单条内联
   `#[cfg(debug_assertions)] debug_assert_eq!(…);`。）
2. **首次运行 level.dat 写失败（上游既有缺陷）**：`write_world_info` 直接
   `File::create("world/level.dat_new")`，而首运行时 `world/` 目录尚不存在 →
   NotFound → `InfoNotFound`，level.dat 静默不落盘（之后目录被维度加载创建，
   下次保存才成功）。修复：写前 `create_dir_all(level_folder)`。
   修复后冒烟验证：首运行即写出 level.dat（496B）+ `world/data/`。

## 1.21.11 客户端进服断连修复（2026-09-19，`No value with id 33774`）

**现象**：1.21.11（Fabric）客户端进服即断连，客户端栈：
`level_chunk_with_light` → `PalettedContainer.read` → `LithiumHashPalette`
抛 `No value with id 33774`。

**根因**：v1_18.rs 区块序列化里的方块状态 remap 门控写的是
`if version < &CURRENT_MC_VERSION`（packet.rs 的**协议目标**）。
版本切换把它改成 V_1_21_11 后，1.21.11 连接判断为 false → **remap 被跳过** →
26.3 数据集的原始状态 id（如 33774）直接上线。方块状态是客户端冻结注册表
（登录不同步），id 空间比 26.3 小，客户端查表必然失败。

**修复**：新增 `pumpkin_data::NATIVE_DATA_VERSION = V_26_3`（数据集原生版本，
与协议目标**刻意解耦**），门控改为 `if version < &NATIVE_DATA_VERSION`。
语义：注册表 id 只有在连接版本 == 数据集版本时才线兼容，更老一律翻译。

**回归测试**：`chunk_data_remaps_block_states_for_1_21_11`
（pumpkin crate）：从 remap 表挑一个 26.3↔1.21.11 id 不同的状态（实测 27→17），
同一区块分别按 V_1_21_11 / V_26_3 序列化，解析区段缓冲断言——
1.21.11 调色板含翻译后 id 且**不含**原始 id，26.3 含原始 id。
已做负向验证：临时恢复旧门控，测试失败（"must receive the translated id 17
(raw 27)"），还原后通过。

**同轮次审计（结论均为无需改动）**：
- 其余 V_26_x 字面量门控（item_stack/bit_set/login_success/explode/particle/
  player_spawn_data/entity_position_sync/entity_animation 等）编码的是历史格式
  变化，1.21.11 全部正确走旧分支。
- ~~群系是登录时注册表同步（login.rs 顺序分配 id 0..N），区块调色板无需 remap。~~
  **此结论有误**，详见下节：同步表本身按版本漂移，群系调色板必须 remap。
- block_update / multi_block_update / level_event / spawn_entity 的方块状态
  remap 本就无条件执行，正确。
- packet.rs `to_id` 未列举版本回退 `_ => v1_21_11`（原为 26.3）。
- `pumpkin_world::CURRENT_MC_VERSION` 字符串 26.3→"1.21.11"
  （仅 level.dat Version.Name / query / crash 报告展示用；区块 DataVersion 走
  独立的 `WORLD_DATA_VERSION`，不受影响）。

验证：pumpkin 315、pumpkin-world 230、pumpkin-protocol 116、pumpkin-data 63
测试全过；`cargo check --workspace` 通过；clippy 我方代码 0 告警。

## 同步注册表 id 空间修复（2026-09-20，完全兼容性审计第二轮）

**问题**：登录/配置阶段下发的"动态注册表"（群系、伤害类型等）的 id 是服务端
按 `REGISTRY_V_<version>` 表顺序分配的（= 该版本 datapacks 目录文件名排序），
而运行时数据（区块群系调色板、伤害事件）写的是 **26.3 数据集 id 空间**。
两套空间随版本漂移：

- `worldgen/biome`：26_3 有 67 个群系，1_21_11 只有 65 个
  （`dappled_forest`、`sulfur_caves` 为 26.x 新增）；65 个共有群系中 57 个
  id 错位。后果：发送含 26.x 群系的区块 → 客户端调色板越界（断连级）；
  其余群系 → 颜色/环境全部错乱（plains 41↔40 等）。
- `damage_type`：`sulfur_cube_hot` 26.x 新增，其前插入使 8 个 id 错位
  → 伤害动画/音效类型错乱。
- `jukebox_song`：`bounce` 26.x 新增，17 个 id 错位（当前无封包使用，未接线）。
- 其余同步注册表（chat_type/dimension_type/trim/变体/画/painting 等）
  两版本集合与顺序完全一致，无需处理。

**修复**（与方块 remap 同架构，数据源改用自家 datapacks 目录）：
- 新 codegen 模块 `tools/pumpkin-codegen/src/sync_id_remap.rs` →
  生成 `crates/pumpkin-data/src/generated/sync_id_remap.rs`：
  对每个"成员或顺序与 26.3 漂移"的同步注册表 × 每个版本，生成
  `<REG>_SYNC_REMAP_V_26_3_TO_V_<ver>: &[u16]`（数据集序 → 该版本同步序）
  与 `remap_<reg>_id_for_version` 分发函数（native 恒等，未知版本恒等）。
  缺失条目回退到近邻占位（dappled_forest→forest、sulfur_caves→dripstone_caves、
  sulfur_cube_hot→hot_floor、bounce→cat）。
- 接线点 1：`v1_18.rs` 区块序列化——群系调色板 Single/Indirect/Direct
  三形态全部重映射（与方块 remap 同一个 `version < NATIVE_DATA_VERSION` 门控）。
- 接线点 2：`damage_event.rs` 写包时重映射 `source_type_id`
  （在协议层做，天然支持同世界多版本客户端）。
- 回归测试 ×3（均已负向验证或表校验）：
  `biome/damage_type_sync_remap_matches_1_21_11_registry`（pumpkin-data，
  校验 plains 41→40、forest 22→21、dappled_forest→forest、
  sulfur_cube_hot→hot_floor、全部表值不越界）；
  `chunk_data_remaps_biomes_for_1_21_11`（pumpkin，区块级，已做
  "禁用 remap 必红"的负向验证）；`damage_event_remaps_source_type_for_1_21_11`。

**经验**：动态（同步）注册表的 id 空间是"服务端下发什么客户端就认什么"，
但它必须与所有后续引用（区块调色板、伤害事件等）同空间；不能因为"登录会同步"
就推断"无需 remap"——同步表本身是按版本生成的。与硬编码注册表（方块状态/物品/
音效等，走 viarewind 链）是两套独立的 remap 体系。

验证（本轮）：pumpkin 316、pumpkin-data 65、pumpkin-protocol 117、
pumpkin-world 230 全过；fmt 干净；clippy 我方代码 0 告警。

## 已知边界

- `sections` 内部由 Pumpkin 全权重建（vanilla section 无额外键，无损失面）。
- Linear/Pump 格式不感知 `.mcc`/oversized（它们本就不是 vanilla 格式；Anvil 是默认）。
- Custom(127) 压缩仍只读不写（无算法定义）。
